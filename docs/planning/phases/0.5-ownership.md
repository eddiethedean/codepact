# 0.5 — Explicit ownership and lexical borrowing

Status: **Planned**. Target first release: **0.5.0**. No gate is currently marked passed.
Owner: maintainer to assign before implementation. Legacy mapping: M3 / implementation Phase 3.

## Outcome

Introduce opt-in transfer checking with visible alias and escape boundaries.

## Entry gate

The preceding minor phase's required gates are accepted, or an explicit scope/dependency amendment has been recorded in the root roadmap. Reuse its supported corpus and baseline metrics.
Before work begins, turn the work packages below into issues with owners and acceptance evidence. Apply the [common release gates](../release-gates.md).

## Work packages

1. Specify and implement Owned[T], move and lexical Borrowed regions in the canonical engine.
2. Separate object lifecycle from handle validity, and carry cleanup obligations through transfers.
3. Validate caller preconditions and supported callee effects using bounded cross-module summaries.
4. Handle known alias conflicts, closures, globals, containers and unknown callbacks conservatively.
5. Define recursion fixed points, widening and trusted-summary provenance.

## Required exit gates

- [ ] **O01** — move transfers the modeled obligation and invalidates the source handle; reuse and double transfer are diagnosed.
- [ ] **O02** — A transfer performed during argument evaluation remains effective if the callee raises. Moving an object does not automatically close it.
- [ ] **O03** — Ordinary assignment retains alias semantics; known conflicting live aliases block a claimed unique transfer.
- [ ] **O04** — Borrowed values cannot be consumed, closed or escaped within the checked subset; supported bodies are verified against their summaries.
- [ ] **O05** — Unknown/native calls, container storage and closure capture never create uniqueness evidence. Strict mode rejects unresolved relevant boundaries.
- [ ] **O06** — Equivalent and mixed-interface fixtures agree across local and supported interprocedural flows, including recursive analysis budgets.

## Evidence to retain

A reviewed transfer/alias truth table, counterexample corpus, summary provenance report and experimental ownership tutorial.
Complete a [release evidence record](../release-evidence-template.md) for the exact candidate revision. Link each gate to test results, fixtures, decisions or reviewed reports. A checkbox without evidence is pending.

## Hold and recovery policy

Ship ownership only as opt-in experimental analysis. If a counterexample invalidates a claimed guarantee, repair the rule or reduce its supported scope before release.
A failed required gate blocks the tag. Patch releases fix behavior within the published scope; moving a required feature out of scope requires a documented plan amendment.

## Deferred scope

Non-lexical lifetimes, arbitrary returned borrows and memory-safety guarantees are deferred.

## Release review

Review the phase gates together with G1–G8, publish limitations and changed diagnostics, then authorize the release tag separately. 0.5.x follow-ups retain these obligations and add regression evidence for each fix. See the [root roadmap](../../../ROADMAP.md).

Use the [shared architecture](../architecture.md) and [migration/query specification](../analyzer-migration.md). These obligations extend the existing phase gates.

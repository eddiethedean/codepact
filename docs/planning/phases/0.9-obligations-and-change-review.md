# 0.9 — Persistent obligations and before-and-after review

Status: **Planned; all new gates pending**. Target first release: **0.9.0**.
Owner: maintainer to assign before implementation. Historical technical milestone and subsystem IDs are unchanged.

## Outcome

Keep responsibility visible after a result is assigned, aliased or forwarded, and review a change against a trustworthy before-state. Demonstrate reviewed library contracts, before-and-after review and obligations that survive assignment together.

## Dependencies and entry gate

Require 0.8 provider/provenance and lifecycle foundations. The 0.7 must-use preview remains released. Persistent acknowledgment, provisionally called MustHandle, requires OH01 semantics; this is not a claim that 0.7 already tracked every assigned result.

## Required exit cases

- [ ] OH01–OH07 qualify every named [v1 outcome acceptance case](../persistent-outcomes.md#required-acceptance-cases). Assignment, equality, aliases, overwrite and deletion cannot erase or merge duties. Finite variants retain path-specific acknowledgment, including guard, wildcard, renewal and finally behavior. Unknown helpers/carriers produce a boundary rather than a false definite last-carrier loss.
- [ ] OH01 production/compatibility controls pass: unmarked Result/Option constructions create no duty, released @must_use assignment behavior is preserved, and unrelated database result types do not acquire MustHandle semantics. Parameter/local/field/nested or resource-payload declarations outside v1 retain explicit boundaries. A successful marked return forwards one existing pending duty without duplication, otherwise creates one outward duty; a call raising before delivery creates no caller token. Qualified direct-await production has its own creation and cancellation controls.
- [ ] **AS03/MP03/BR01** distinguish stop requested, underlying work completed, exception/result observed, typed result acknowledged and resource cleaned. Cover stored-but-never-observed work, alias observation, timeout, rejected cancellation, worker exception and an observed ordinary result containing a new outcome duty.
- [ ] **BR01** distinguishes Future.running from actual worker execution: the running state may establish only that cancellable dispatch has passed. Executor context exit does not itself observe every submitted result.
- [ ] CR01–CR09 qualify every named [v1 review acceptance case](../change-review.md#required-acceptance-cases); CR04/CR05 enforce its preservation prerequisites and verdict/exit table. Missing required coverage, ambiguous required correspondence or incomparable semantics cannot pass preservation. Relevant policy/scope/contract/waiver/assumption changes require deliberate acceptance under the selected review policy; stale after inputs cannot validate the current workspace. A completed failed, review-required or inconclusive review exits 1; invalid input/execution failure exits 2. Preserve valid inherited findings without misclassifying them as regressions.
- [ ] Before-and-after review catches a new leak/duty while retaining clean line-shift controls. Definite-to-unknown, exclusion, policy relaxation, lost provider applicability, target migration and exhausted budgets cannot masquerade as a source repair; a clean local diff cannot hide changed dependency/caller scope.
- [ ] HTTPX, HTTPX2, SQLAlchemy and SQLModel each have a pinned valid/invalid/boundary matrix. Direct-await profiles promote separately. Response/body state, transaction settlement, session reuse, result consumption and cleanup remain distinct facts.
- [ ] **AS07** passes before promoting the named sharing profiles: concurrent requests with an open shared HTTPX client and an open shared HTTPX2 client are independent valid controls; separate SQL sessions per task are valid; known overlapping operations on one AsyncSession and close during known active use are invalid. Unknown aliases, task graphs or operations retain incomplete coverage. An unsupported-only control does not qualify the required overlap check, and generic BorrowedMut rules are unchanged.
- [ ] LC10's exact-artifact session_scope summary passes controlled normal, exceptional and cleanup-failure conformance. An Exception path has modeled rollback; other exceptional exits and failed commit/rollback/close retain only their separately established effects. Generator-source verification and request_scoped_session framework/dependency lifetime checking remain LC11/PC03 work in 0.11–0.12.
- [ ] **E12** passes in full under the unchanged [definition](carry-forward-gates.md#e12), including strict failure on incomplete coverage regardless of baseline disposition.
- [ ] **E10-B** passes the mandatory [artifact-comparison checkpoint](carry-forward-gates.md#mandatory-e10-checkpoints) through installed author tooling, with compatible, new-caller-obligation and insufficient-evidence controls plus CLI/Rust and fresh/reused parity. Requalify E10-A when affected; the composite gate stays pending.

## Scope boundaries

Waiting for work or exiting an executor does not establish result observation. Retrieving an ordinary result does not automatically acknowledge an embedded outcome. Resource-payload ownership remains conditional on TypePact TC03/OH08; matching or wrapping creates no implicit transfer, cleanup or completion.

General field/container storage is not silently included. OH09 custom adapters and OH10 richer carriers require explicit semantics and qualified PC02 in 0.12. A separately named async profile remains unqualified until its own evidence passes even if its synchronous counterpart is supported.

## Evidence and release decision

Retain the exact candidate, model/provider artifact identities, selected Python/platform/start-method profiles, fixture IDs, valid/invalid/unknown cases, diagnostics/coverage, fresh/reused parity and costs in the [release evidence record](../release-evidence-template.md). Controlled upstream conformance fixtures are separate from static analysis; never import or execute the user's target project.

All required work and applicable [G1–G8](../release-gates.md) remain pending until evidence and the maintainer's decision establish completion. A missing gate blocks release or requires an explicit reviewed scope amendment. This plan does not authorize tagging or publication. Patch releases stay within the qualified 0.9.x scope.

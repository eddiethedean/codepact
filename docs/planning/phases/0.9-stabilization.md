# 0.9 — Stabilization and 1.0 readiness

Status: **Planned**. Target first release: **0.9.0**. No gate is currently marked passed.
Owner: maintainer to assign before implementation. Legacy mapping: M5 stability portion / implementation Phase 5.

## Outcome

Establish a stable core with evidence for its guarantees and maintenance commitments.

## Entry gate

The preceding minor phase's required gates are accepted, or an explicit scope/dependency amendment has been recorded in the root roadmap. Reuse its supported corpus and baseline metrics.
Before work begins, turn the work packages below into issues with owners and acceptance evidence. Apply the [common release gates](../release-gates.md).

## Work packages

1. Freeze the proposed 1.0 core APIs, canonical semantics, diagnostic codes and configuration/output schemas.
2. Audit limitations, trusted summaries and unresolved soundness reports across every supported feature.
3. Run full compatibility, interoperability, fuzzing, platform and pilot regression suites.
4. Finalize deprecation rules, backport policy, ownership of modules and private vulnerability reporting.
5. Rehearse release and partial-publication recovery without publishing an unintended version.

## Required exit gates

- [ ] **S01** — All required gates from prior phases have evidence or a reviewed scope change that removes the affected support claim; no unsupported feature is labeled stable.
- [ ] **S02** — No unresolved critical soundness issue, analyzer crash on the supported corpus, or unexplained cross-interface mismatch remains.
- [ ] **S03** — At least two successive candidate revisions pass the full supported matrix with no new blocking regressions; record exact revisions and artifact hashes.
- [ ] **S04** — Migration documentation covers every breaking 0.x change; a representative pilot upgrades using those instructions.
- [ ] **S05** — Release artifacts, licensing, source provenance, installation, trusted publishing and crates token setup are verified; partial-publish recovery has a written rehearsal record.
- [ ] **S06** — Named maintainers accept the 1.0 scope, support window, deprecation policy, public limitations and security reporting process.

## Evidence to retain

A 1.0 readiness report, signed-off gate evidence, candidate comparison, migration guide, benchmark report and release rehearsal record. Approval is a recorded maintainer decision, not inferred from CI success.
Complete a [release evidence record](../release-evidence-template.md) for the exact candidate revision. Link each gate to test results, fixtures, decisions or reviewed reports. A checkbox without evidence is pending.

## Hold and recovery policy

Continue with 0.9.x fixes while blockers remain. Re-scope explicitly or defer 1.0; reaching the version number does not establish readiness.
A failed required gate blocks the tag. Patch releases fix behavior within the published scope; moving a required feature out of scope requires a documented plan amendment.

## Deferred scope

Research features may remain experimental after 1.0 and must be excluded from stable guarantees.

## Release review

Review the phase gates together with G1–G8, publish limitations and changed diagnostics, then authorize the release tag separately. 0.9.x follow-ups retain these obligations and add regression evidence for each fix. See the [root roadmap](../../../ROADMAP.md).

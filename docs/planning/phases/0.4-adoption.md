# 0.4 — Adoption tooling and useful preview

Status: **Planned**. Target first release: **0.4.0**. No gate is currently marked passed.
Owner: maintainer to assign before implementation. Legacy mapping: M2 part 2 / implementation Phase 2.

## Outcome

Make lifecycle analysis practical for existing repositories and CI.

## Entry gate

The preceding minor phase's required gates are accepted, or an explicit scope/dependency amendment has been recorded in the root roadmap. Reuse its supported corpus and baseline metrics.
Before work begins, turn the work packages below into issues with owners and acceptance evidence. Apply the [common release gates](../release-gates.md).

## Work packages

1. Implement validated pyproject configuration, explicit target versions and deterministic precedence.
2. Add versioned JSON diagnostics, documented exit codes, advisory/strict modes, rule-specific suppressions and baselines.
3. Implement the initial must-use rule for discarded expressions, with equivalent decorator and annotation forms.
4. Document unsupported-boundary summaries and strict-mode failure behavior.
5. Run pilots and refine onboarding, diagnostic explanations and triage workflows.
6. Specify the [lint command and reporting foundations](../linting-and-editors.md) (LE01): shared diagnostic/configuration policies, a versioned machine report and a location-per-line format for editor external tools. Qualify LE-V01/LE-V02 for CLI reporting; language-server and client delivery remains in 0.8.
7. Deliver [AI-agent workflow foundations](../ai-agent-integration.md) AI01–AI03: versioned schemas/capabilities, bounded repair context and an opt-in project instruction recipe for checking, editing and rechecking with explicit coverage.

Concurrency work: Extend reports and explanations with modeled task/resource origins, close/transfer and suspension/escape sites. Include at least one async application among the existing pilot minimum, separating unsupported concurrency patterns from confirmed violations. Follow [CS02](../concurrency.md) for the exact supported subset and evidence.

## Required exit gates

- [ ] **A01** — CLI exit codes 0/1/2 distinguish below-threshold findings, actionable findings and execution/configuration failure; JSON fixtures match the versioned schema.
- [ ] **A02** — Baselines suppress only matching existing findings; new findings, new rules and changed fingerprints are surfaced. Updating a baseline is an explicit operation.
- [ ] **A03** — Invalid keys and versions fail clearly; includes, excludes, path resolution and precedence have deterministic fixtures.
- [ ] **A04** — @must_use and MustUse[T] produce equal obligations; bare discard, explicit discard and assignment follow documented semantics.
- [ ] **A05** — At least three representative pilot projects are reviewed. At least 90% of definite-violation findings in a recorded sample of at least 30 are actionable; disclose counts, selection and disagreements. Insufficient evidence holds this gate.
- [ ] **A06** — No supported-scope correctness blocker or unexplained frontend parity failure remains; onboarding from installation to a useful check is reproduced in a clean environment.
- [ ] **CS02** — Complete the phase requirements in the [concurrent resource safety plan](../concurrency.md); retain valid, invalid and unsupported-boundary fixtures and fresh/reused parity for the claimed subset.

## Evidence to retain

Pilot scorecards, labeled diagnostic samples, schema fixtures, baseline regression cases and a first-use walkthrough. Pilot targets are engineering acceptance goals, not current measured claims.
Complete a [release evidence record](../release-evidence-template.md) for the exact candidate revision. Link each gate to test results, fixtures, decisions or reviewed reports. A checkbox without evidence is pending.

## Hold and recovery policy

Reduce the default rule set if triage quality fails. Keep experimental rules opt-in and repeat evaluation after changing semantics.
A failed required gate blocks the tag. Patch releases fix behavior within the published scope; moving a required feature out of scope requires a documented plan amendment.

## Deferred scope

Whole-program ownership and a replacement for ordinary Python type checking are deferred.

## Release review

Review the phase gates together with G1–G8, publish limitations and changed diagnostics, then authorize the release tag separately. 0.4.x follow-ups retain these obligations and add regression evidence for each fix. See the [root roadmap](../../../ROADMAP.md).

## Analyzer architecture obligations

Treat rule modes, configuration and baseline/reporting policies as explicit inputs. Separate semantic results from presentation/suppression so reporting changes cannot create semantic certainty.

Use the [shared architecture](../architecture.md) and [migration/query specification](../analyzer-migration.md). These obligations extend the existing phase gates.

- [ ] **A07** — Changing settings refreshes the relevant diagnostics and coverage while preserving canonical facts where semantics are unchanged; fresh and reused sessions agree.
- [ ] **A08** — Complete AI01–AI03 and AI-V01–AI-V04 for CLI workflows in the [AI-agent plan](../ai-agent-integration.md), with a recorded repair walkthrough. Structured results preserve certainty/coverage and detect stale or truncated output; a repair cannot pass by weakening project policy.

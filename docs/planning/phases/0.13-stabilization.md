# 0.13 — Stabilization and 1.0 readiness

Status: **Planned; all new gates pending**. Target first release: **0.13.0**.
Owner: maintainer to assign before implementation. Original M5 stability and implementation Phase 5 commitments are retained.

## Outcome

Make a recorded 1.0 readiness decision from qualified behavior, adoption and maintenance evidence. The version number alone does not establish stable support.

## Dependencies and entry gate

Require preceding applicable gates or an explicit reviewed scope amendment removing the affected claim. All original S01–S09 definitions remain unchanged in the [carry-forward registry](carry-forward-gates.md#stabilization-gates).

## Required deliverables

| Work | Completion requirement |
| --- | --- |
| Stable contract | Audit public APIs, canonical semantics, diagnostic/configuration/output schemas, manifests, capabilities, applicability and trusted-summary limits. |
| Compatibility and correctness | Full supported interoperability, fuzz, platform and pilot suites; soundness/crash/interface audit and bounded memory. |
| Provider and policy upgrades | Actual-wheel compatible/breaking/unknown changes plus preview-to-baseline-to-strict adoption and stale-model repair. |
| Concurrency claims | CS07 audit of each named async/process/thread model and retained counterexample; explicit stable, preview and unsupported profiles. |
| Maintenance and releases | Owners, support/deprecation/backport/security policies, migrations, provenance and partial-publication recovery. |

## Required exit cases

- [ ] **S01–S09** pass in full, including two successive candidate revisions passing the supported matrix with exact revisions and artifact hashes.
- [ ] **CS07** completes its unchanged stable-scope audit across historical CS01–CS05 and the qualified AS/MP/BR catalogs.
- [ ] A representative pilot follows migration instructions for every applicable breaking 0.x change. Environment modernization remains distinct from unchanged-contract repair.
- [ ] Real-wheel upgrades demonstrate compatible, breaking and unknown behavior with applicability/provenance, baseline and CLI/editor parity.
- [ ] Preview/baseline/strict adoption retains incomplete-coverage failures through a dependency upgrade, stale model and repair. Record stable opt-in, preview and deferred policies.
- [ ] Release/partial-publication recovery is rehearsed without publishing an unintended version. The maintainer records readiness and separately authorizes any eventual release.

## Hold and stable boundary

Continue qualified 0.13.x fixes, explicitly reduce scope or defer 1.0 while blockers remain. Experimental work can stay outside stable guarantees. Do not claim generic race/deadlock freedom, arbitrary Python memory safety, universal serialization or general ownership across threads/processes.

Freeze public schemas independently from internal Salsa representations. Retain the complete edit/invalidation and dependency-upgrade corpus with bounded memory. A CI success, clean report or roadmap checkbox cannot substitute for a recorded readiness decision.

## Evidence and release decision

Retain the exact candidate, model/provider artifact identities, selected Python/platform/start-method profiles, fixture IDs, valid/invalid/unknown cases, diagnostics/coverage, fresh/reused parity and costs in the [release evidence record](../release-evidence-template.md). Controlled upstream conformance fixtures are separate from static analysis; never import or execute the user's target project.

All required work and applicable [G1–G8](../release-gates.md) remain pending until evidence and the maintainer's decision establish completion. A missing gate blocks release or requires an explicit reviewed scope amendment. This plan does not authorize tagging or publication. Patch releases stay within the qualified 0.13.x scope.

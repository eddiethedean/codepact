Status: **Implementation complete; release qualification and maintainer decision tracked in the [candidate evidence](../../releases/0.1.0-evidence.md)**. Target: **0.1.0 foundational preview**. Record qualification evidence and maintainer decisions before release.

## Release outcome

A developer can install the Python helpers, build the Rust crate and inspect canonical contracts from a small Python module without importing it. The Rust crate provides a usable inspection API and a thin CLI backed by the same implementation.

0.1 proves contract representation, compatibility and delivery. Resource flow checking begins in 0.2. Inspection output must state that it does not establish runtime correctness, ownership or lifecycle safety.

## Scope and artifacts

| Artifact | Required 0.1 behavior |
| --- | --- |
| Python distribution typepact | Lightweight resource decorator and typed ownership/access metadata aliases; typing marker; no native analyzer loaded at import |
| Rust crate typepact | Parse and resolve the supported declaration subset; lower both interfaces into canonical contracts; return contracts, diagnostics and coverage |
| Rust CLI typepact | inspect-contracts command with versioned deterministic JSON, source locations and explicit inspection-only status |
| Examples | Paired contract fixtures and a mixed-interface Connection example that the inspector can read |
| Distribution | Python wheel and source archive plus a buildable crate; versions aligned at 0.1.0 |
| Documentation | Installation, inspection walkthrough, supported syntax, diagnostics, limitations and 0.2 handoff |

Selected delivery under D015: the pure Python typepact package depends on an exactly matching typepact-cli package, which distributes the Rust executable through maturin. Release builds target Linux glibc/musl, macOS and Windows on x86-64/ARM64. Python imports remain lightweight. A complete source archive supports local Rust builds; the Rust crate remains available on crates.io.

The explicit low-level Resource metadata used by the prototype is provisional. Owned and Borrowed express access intent; they do not create a resource lifecycle contract or prove uniqueness. Equivalent declarations compare only dimensions they actually share.

## Required exit gates

Preserve F01–F05 as existing gate identities; the requirements below clarify them. F06–F08 make the usable deliverable and qualification explicit.

- [ ] **F01 — Canonical interoperability.** Captured alias views preserve declaration identity through rebinding. Equivalent Pythonic/explicit lifecycle declarations and equivalent verbose/shorthand access annotations produce equal semantic facts under the comparison rules in the prototype spec. Mixed declarations merge independent dimensions; conflicts produce declaration errors. Retain golden snapshots.
- [ ] **F02 — Python compatibility.** Each claimed interpreter imports helpers and evaluates supported annotations. Pinned mypy and Pyright fixtures preserve base types and report intended ordinary type errors. Decorators preserve class identity; ordinary values retain identity. Native analyzer loading is absent from helper imports.
- [ ] **F03 — Source handling.** The complete supported/invalid/unsupported fixture matrix passes, including aliased imports, symbol shadowing, multiline AST declarations, syntax errors and target-version boundaries. AM01–AM03 evidence is required. A side-effect fixture is inspected with its marker file absent afterward; imports and annotation expressions are never executed.
- [ ] **F04 — Reproducible delivery.** Clean source builds produce matching-version Python wheel/source archive and a verifiable typepact crate with a working inspector. Source archives contain needed code and license files. Clean artifact installations, CLI/API smoke checks, Python metadata validation and Cargo dry run pass.
- [ ] **F05 — Release prerequisites.** License, registry ownership, GitHub pypi environment, initial PYPI_API_TOKEN configuration (trusted publishers after both PyPI projects exist), Cargo secret configuration, support matrix and source-build instructions are recorded. Evidence records secret presence/configuration only; never token contents.
- [ ] **F06 — Useful inspection.** Rust API and CLI inspect the paired and mixed fixtures consistently, emit deterministic schema-v0 output and distinguish declaration errors, incomplete inspection and success using documented exit codes. Output explicitly states inspection-only assurance. AM04–AM06 must prove fresh/updated-session parity, no-op reuse, dependency isolation, settings invalidation and bounded recovery.
- [ ] **F07 — Quality gates in CI.** Pull-request/push checks exercise the applicable validation matrix. Both registry publication jobs depend on those checks for the tagged revision, not merely an earlier branch run. All required checks pass on the candidate.
- [ ] **F08 — User and handoff readiness.** A clean-environment walkthrough reproduces installation and inspection. Public docs state the shipped subset, combined Python helper/CLI installation and source-build prerequisites and deferred enforcement. The 0.2 backlog names the remaining CFG, alias, summary and lifecycle work.

Each gate requires the evidence identified in the [validation matrix](0.1/validation.md). Local implementation exists, but this plan does not claim gate completion or external publisher verification.

## Candidate and release procedure

1. Complete WP01–WP06 and resolve all required gate failures.
2. Review WP07 with the actual advertised interpreter/platform/toolchain matrix.
3. Create a candidate evidence record for the exact commit, including artifact hashes and tool versions.
4. Pass F01–F08 and common gates G1–G7. Record maintainer authorization separately.
5. Only then push v0.1.0 through the existing stable-tag workflow.
6. Verify both registries, download/install the published artifacts and complete G8.

Candidates are commits and CI artifacts. The current release workflow does not accept prerelease suffix tags. Publishing is a separate action from refining this plan.

## Hold criteria and scope control

A placeholder crate, inspector that executes target Python, unresolved frontend disagreement, rejected public aliases, broken advertised installation or absent licensing holds the release. Keep failed gates pending/failing and record remediation in the work item.

A failed shorthand prototype can fall back to verbose Annotated only after the API docs and gate expectations are updated. A reduced support matrix requires an explicit decision and corresponding compatibility documentation. Dropping the usable inspector or either registry artifact requires a roadmap scope amendment.

0.1.x fixes preserve the declared inspection semantics; broader contract enforcement belongs in a later minor phase. Patch releases retain relevant F and G gates and add regression coverage for each correction.

## Deferred work and 0.2 handoff

0.1 does not implement flow-sensitive close/use checks, cleanup obligations, move enforcement, borrow escape analysis, finite typestate, Result/Option runtime values, framework adapters, editor integration or persisted caches. In-memory Salsa memoization and a reusable session are required foundation work.

The handoff must include resolved contracts with provenance and spans, bounded name resolution, inspection fixtures, supported-syntax documentation, packaging evidence and performance baselines. Create 0.2 work items for CFG construction, resource-instance identities, local alias tracking, normal/exceptional method summaries and the first use-after-close diagnostic. Declaration IDs in 0.1 must not be mistaken for runtime object identities.

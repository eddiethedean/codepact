# 0.1 — Foundations and feasibility

Status: **Planned**. Target first release: **0.1.0**. No gate is currently marked passed.
Owner: maintainer to assign before implementation. Legacy mapping: M0 / implementation Phase 0.

## Outcome

Prove both APIs can describe the same contract and establish buildable Python and Rust packages.

## Entry gate

The product direction and canonical-engine approach are accepted. Assign an accountable owner and review the initial API and packaging choices.
Before work begins, turn the work packages below into issues with owners and acceptance evidence. Apply the [common release gates](../release-gates.md).

## Work packages

1. Choose the parser, Rust MSRV, supported Python versions and package delivery approach in decision records backed by prototypes.
2. Create the root Cargo workspace, typepact engine crate, Python build manifest, committed Cargo.lock, typing metadata and license.
3. Define canonical IR v0, source spans, resource identities, provenance and diagnostic structure.
4. Prototype Pythonic resource lowering and Annotated-compatible explicit aliases; keep runtime imports independent of the native analyzer.
5. Create the fixture harness and CI checks for Python imports, Rust builds and cross-interface lowering.

## Required exit gates

- [ ] **F01** — A Pythonic resource declaration and its equivalent explicit contract produce equal canonical semantic fields, excluding source provenance.
- [ ] **F02** — Pinned mypy and Pyright runs accept the chosen public aliases and preserve their underlying Python types; all claimed Python versions import the API successfully.
- [ ] **F03** — Parser fixtures cover supported syntax versions, shadowed names, imported aliases and syntax errors; analysis never imports target modules.
- [ ] **F04** — Clean builds produce an installable Python distribution and a verifiable typepact crate with matching versions. Cargo dry run and Python metadata checks pass.
- [ ] **F05** — License, registry ownership, publisher configuration, source-build instructions and an actual artifact support matrix are recorded.

## Evidence to retain

Parser comparison, alias compatibility report, canonical snapshots, clean-install logs and a packaging decision. Publish only an explicitly labeled foundational preview with a usable engine API or demonstrator.
Complete a [release evidence record](../release-evidence-template.md) for the exact candidate revision. Link each gate to test results, fixtures, decisions or reviewed reports. A checkbox without evidence is pending.

## Hold and recovery policy

A metadata-only helper package or prototype CLI may ship with precise limits. A placeholder crate with no useful behavior does not satisfy this gate. Resolve alias or packaging failures before scheduling 0.2.
A failed required gate blocks the tag. Patch releases fix behavior within the published scope; moving a required feature out of scope requires a documented plan amendment.

## Deferred scope

Use-after-close checking and general ownership enforcement are deferred to later phases.

## Release review

Review the phase gates together with G1–G8, publish limitations and changed diagnostics, then authorize the release tag separately. 0.1.x follow-ups retain these obligations and add regression evidence for each fix. See the [root roadmap](../../../ROADMAP.md).

## Performance comparison

The release baseline is published 0.7.0. The optimized capture alternates
baseline and candidate processes for inherited state, exclusive and executor
workloads. The candidate-only workload checks an installed manifest backing a
64-function caller and verifies fresh-session parity after a provider upgrade
and an independent edit. [Benchmark capture](../../scripts/capture_phase08_performance.py)

The exact-candidate capture used 24 alternating process pairs per workload on
macOS 26.5.2 ARM64 with Rust 1.96.0. Time changes below are paired medians.
Peak RSS is the maximum measured process RSS in each arm.

| Workload | Cold | Unchanged session | Affected edit | Unrelated edit | Peak RSS increase |
| --- | ---: | ---: | ---: | ---: | ---: |
| State | −0.32% | +1.60 µs (+18.60%) | −0.27% | +2.42% | 1.66 MiB |
| Exclusive | −0.07% | +1.67 µs (+17.37%) | −0.15% | +3.11% | 1.19 MiB |
| Executor | +1.14% | +0.38 µs (+16.20%) | +0.91% | +0.70% | 1.84 MiB |

The installed-manifest workload measured medians of 4.318 ms cold, 0.274 ms
unchanged, 3.858 ms after the provider upgrade and 0.124 ms after the unrelated
edit, with peak RSS of 9.98 MiB.

The preceding 12-pair replay and the earlier 20-pair exclusive replay also
measured microsecond-scale increases for unchanged checks. The warm check
includes input validation, cached query retrieval and result construction.
Fresh/reused tests verify query reuse and caller refresh after a provider
upgrade. The measured warm-session and memory increases were accepted in the G4
signoff. [Earlier measurement](../planning/phases/0.8/implementation-evidence.md)

The local raw receipt is `target/final-verification/release-3ca2623-performance.json`
with SHA-256 `ed187b5430014e19933368d30bb37c857f02e10a5ae552b397f7ce8e9644f6b9`.
Reproduce with `CODEPACT_PHASE07_PROCESS_REPEATS=24` and the linked capture
script against optimized `benchmark_phase06` binaries at `v0.7.0` and the
candidate and the optimized candidate `benchmark_phase08` binary.
